# 8. Going live, one step at a time

James has pre-approved merging and going live: carry finished, tested work right through. Still ask him on a question card before anything destructive (dropping, deleting, removing pupils' data), and say exactly what will happen. This is the one place that rule lives.

0. **Pre-flight (nothing live).** Merge `origin/main`. Re-check migration numbers (renumber yours if needed) and any shared database functions you re-create ([3-files-and-clashes.md](3-files-and-clashes.md)). Run typecheck, `test:changed`, build (the PR's checks run every test), and your database tests on a scratch copy built from `main`'s migrations plus yours. Check the live database has what you depend on by querying for it (`select to_regclass('public.<table>')`), not by trusting docs.
1. **How going live works: migrations and functions go live by themselves when your PR merges**. "Test and publish" runs every check, then `scripts/apply-live-migrations.sh` applies every migration not yet in the live history (`supabase_migrations.schema_migrations`), then deploys each function whose `supabase/functions/<name>/index.ts` changed, then publishes the site. So: rebuild only your function (`npm run build:functions -- <name>`) and commit its `index.ts`. Nobody pastes SQL or runs deploy commands any more.
   - **Not ready to go live?** Put the migration's number in `supabase/migrations-on-hold.txt`; take it out in the PR that goes live.
   - **Destructive migration** (a line *starting* with `drop table`, `drop schema`, `truncate`, `delete from` or `alter table … drop column`): the job refuses it unless the file has the line `-- live-ok: destructive`. Add that only after James's yes on a card.
   - **Never apply a migration by hand** (SQL Editor, connector) without also adding its history row, or the job will apply it a second time: `insert into supabase_migrations.schema_migrations (version, name) values ('<number>', '<name>');`
   - To redeploy a function that didn't change: Actions → Test and publish → Run workflow, with its name (or `all`).
   - Database checks and site checks also run on every PR: don't merge a red PR. A PR that only changes notes and plans (`docs/`, or a `.md` file at the top level) skips the site checks; one that doesn't touch `supabase/migrations/`, `supabase/tests/` or the Supabase config skips the database checks.
   - **Merges close together are fine**. Each publish works out what changed since the last publish that went green, so a run dropped from the queue or a failed run is caught up by the next one: its migrations, functions and site all go live then. A notes-only merge publishes nothing. After merging, check that a run **after** your merge went green (not necessarily the one started by your merge).
2. **Open the PR and merge it when green** (PR body: [templates/golive-pr.md](templates/golive-pr.md)) (this is the step that goes live: see 1). Merge `origin/main` into your branch one last time, open the PR with the GitHub MCP tools, wait for the checks, then merge. Never push from the main checkout.
3. **After the merge, check** the Test and publish run went green, your tables exist and are empty, the game's switch column is **on** for every class (a new game's switch starts on for every class: James, 11 Nov 2026), and an unsigned `curl -X POST …/functions/v1/<name>` answers a 401 message, not a crash or 404.
4. **Check from outside.** Signed out and as a pupil: server-only tables and functions refused (42501), pupils see only their own and their school's rows, older data untouched (e.g. `select count(*) from public.scored_games;` not smaller).
5. **Try it live as a teacher** (teachers can open `/#/<id>` even before the code switch is on).
6. **Switch it on** for pupils: the code switch is what holds the game back, because the teacher switch already starts on for every class. The server must still check the teacher switch on every call, since a teacher can turn it off. Unless James asked to keep it off. The code switch is its own small PR (`ON = true` in `src/games/<game>/switch.ts`, plus your id in `registry.test.ts`). The teacher switch needs nothing from you: its column defaults to true, so the school's defaults row and every new class get it on. If James wants it off for existing classes, that is a normal teacher save from the Games tab, not SQL.
7. **Write it down:** a "went live" note in your plan (what was applied, deployed and checked, when), update project memory, and put the next part's copy-ready prompt on the Games Hub Prompts board.
8. **Mark it finished (every merge, not only go-live).** Every time a branch is merged (not only at go-live), in the same session: change the **Status** line at the top of the plan to say what is live and which PR merged it, fix any other doc that still calls it "not live" or names the branch (`grep -rn "<branch>" docs/`), then delete the merged branch (`git push origin --delete <branch>`). A finished branch left on GitHub, or a plan still saying "not merged", makes the next session think the work is unfinished.

**Turning it off again (rollback), from gentlest to strongest:**
- **The teacher switch** on the Games tab (Admin, New class settings, for classes made later). Pupils see "not switched on", the data is kept, and the server refuses requests (make sure your function checks the switch itself).
- **The code switch** set to `false` and published: the card disappears.
- **Delete the function** in the Supabase dashboard: everything that needs the server stops.
- **Database:** don't drop tables. Write a new migration if something must change. Never roll back with SQL on `app_settings` (one row per class): use the Teacher page.
