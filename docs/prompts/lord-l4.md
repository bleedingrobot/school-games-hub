## This step: L.4 (stop for James when done)

**The server is the boss.** Today the browser rolls the dice, picks the monster, decides what a right answer is worth and keeps the hero. After this step none of that is trusted. The shared engine in `shared/lord/` is the rule book; the server runs the same code.

1. **Migration** (a new file in supabase/migrations, in the style of the Maths Monsters one, with a header that says what it does): tables `lord_heroes` (one row per student: the hero as JSON, a version number, the season, the day), `lord_fights` (each fight handed out: monster, seed, kind, the options it started with, the actions it ended with, the result; one open fight per student at a time), `lord_events` (an audit trail of accepted requests, with each one's request id so a repeat counts once) and `lord_refusals` (requests the checks turned down, for the teacher page). Students can't read or write them directly: they read their own through a `my_lord()` function, and only the `lord` server function writes. A teacher switch on `app_settings`: **OFF until a teacher turns it on**, set through a `teacher_set_lord()` function, plus forest fights a day. Row-level security on everything, like the other games. Don't touch points, leaderboards or the "warriors" board yet (L.5).
2. **The `lord` server function** (supabase/functions/lord/: `handler.ts` with tests, then `npm run build:functions` for `index.ts`; the rules come from `shared/lord/`): actions `load`, `start-hero` (pick a class), `forest` (takes one forest fight off today's count and hands out the monster and seed, or an event, chosen by the server), `fight-finish` (the browser sends the actions it played; the server replays them from the saved seed with `replayFight` and only then pays gold and exp; a fight can be finished once), `event` (pays an event; a maths event's reward only for a right answer), `master-start` and `master-finish`, `dragon-stage` and `dragon-finish`, `shop-buy`, `heal`, `bank`, `inn` (riddle, number guess, interest: each once a day), and `rollover` (the first request of a new New Zealand day gives back the day's turns and full health; a new season resets the hero; nothing runs at midnight).
3. **Maths is checked by the server too.** A question answered in the browser arrives as the pack, the key, the numbers and the answer. The server rebuilds the question from the key and numbers (`BandedPack.rebuild`, as `monster` does), decides right or wrong itself, and uses that for the size-it-up bonus, the shop and healer discounts, the master trial strength and the dragon riddles. Whether a fight offers "size it up" comes from the seed (`offersSizeItUp`). A request that claims a right answer it can't prove counts as wrong, never as an error the pupil sees. Record each answer in the same fact tables the other games use (see how Maths Monsters does it) so the teacher's "hardest facts" view keeps working.
4. **Refresh-safe:** a half-finished fight stays on the server (the seed, the monster, the options). Reloading the page, or opening it on another Chromebook, offers it again and the pupil picks up from the start of that fight with no extra fight used. Leaving a fight unfinished and starting another is refused. Sending the same finish twice counts once. A request with an old version number or a repeated id is refused cleanly. Skill uses for the day are shared across all three dragon stages, as in the engine.
5. **Client:** replace the trial's local save in `src/games/lord/` with a small data layer (copy the shape of src/data/monsters.ts: load, queue, retry, "saving later" when offline, a friendly message when it can't save). The screens keep working as they do now; the difference is that `forest`, `master-start`, `dragon-stage` and every purchase wait for the server, and the fight is played in the browser with the seed the server gave. Keep a clear, friendly message for "closed" (switch off) and "can't connect". The **test tools** (`Tools.tsx`) must not work for students: on the server only a teacher account may use them, and they are kept in the browser trial build (`preview/lord`) only.
6. **Tests:** handler tests for every action (a normal day, losing, running away, a master, all three dragon stages, a repeated request, a tampered result, a forged right answer, an old version, a second open fight, the day rolling over at New Zealand midnight and not before, a season ending, the teacher switch off); a replay test that the server and the browser get the same result from the same seed and actions; the SQL tests in supabase/tests/database for the migration (students can't write, can read only their own); client tests for loading, the offline queue and the closed message. If the local Supabase database can run here (`npm run db:start`, `npm run test:db`), run the migration there. **Do not apply the migration to the live database and do not deploy the function.**
