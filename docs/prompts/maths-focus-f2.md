Build F.2:

1. **Schools.** `schools` (name, active, board-approved date, contact teacher), `school_domains` (the email domains a school signs in with; a school can have several), `profiles.school_id` (set once at sign-up from the email domain, never changed by the student). Douglas Park is school 1 with `douglaspark.school.nz`, and every existing profile and every row already saved is moved into it.
2. **Sign-in.** The three checks stay, but "is it a Douglas Park email?" becomes "is the domain in `school_domains` for an active school?". An unknown domain still can't make an account. `school_domain()` and `SCHOOL_DOMAIN` in src/config.ts were written for one school: replace them cleanly and say what you changed. Keep the README's three-locks description true and update it.
3. **`my_school()` everywhere.** One helper, used in every row rule and every `teacher_*` function that shows or changes another person's data, so one school can never read another's students, games, records or settings. Lobbies, game codes, classmate games and leaderboards stay inside a school. Make a checklist of every table and function you touched and every one you decided didn't need it, with the reason.
4. **Roles.** Student, teacher (their own classes), school admin (everyone in their school: makes teachers, archives classes) and site owner (me: adds schools, sees no student data unless needed). `make_first_teacher` keeps working for Douglas Park, and I am its first school admin and the site owner.
5. **Classes.** `classes` (school, name like "Room 12", school year, year level, archived), `class_teachers` (several teachers per class), `class_members` (one current class per student, moving a student just changes the row), `class_groups` and `class_group_members` (optional groups inside a class; the screens for groups come in F.3, but the tables go in now). **Class Warp** (plan section 6b, read it): every class and every group has its own warp code, made the same way as game codes (no vowels or lookalike characters); typing a class code puts the student in that class (asking "Leave Room 12 and warp to Room 14?" first if they are in another), typing a group code puts them in the group and its class; a teacher can turn a code off, reset it, or set it to ask first, and sees warps as they happen; wrong codes say only "That code didn't work" and are rate-limited like game codes; archived classes' codes stop working; and a teacher can still tick students from a list of their school's students who have no class. Groups' tables and warp codes go in now; the group management screens still come in F.3. Teachers see only students in their own classes; the school admin sees every class in their school. Every existing `teacher_*` function gets this check without changing what it returns for Douglas Park teachers: put every current teacher in a default class "Everyone" with every current student, so nothing disappears from their screens on the day this goes live.
6. **Settings per class.** The settings now on `app_settings` become per class, and the school's row becomes the default a new class starts with. Games and teacher pages read the setting of the student's class (or the school default for a student with no class). Say clearly what you decided about students with no class.
7. **Screens.** A small "My classes" page for teachers and school admins: make a class, show its join code, see its members, add a student from the list, move or remove a student, add a co-teacher, archive a class. A **Class Warp** button on the student dashboard and a "Join your class" step for new students (type the code, see the class or group name, confirm, a short warp animation and "Welcome to Room 12!"; skippable, because a student with no class must still play; keep the animation short, calm and switch-off-able for reduced motion). The teacher page shows the codes (turn off, reset, ask-first) and a live "joined" list. Keep the style, wording and accessibility of the existing teacher pages (axe clean at 1366 x 640 and 844 x 390).
