Build T.2:

1. **Database** (a new migration, never editing old ones, following the style of the fact_answers one): a training answers table with one row per answer (student, fact key like `mul:6x7`, right or wrong, answer time in ms, typing time used in ms, the day, when), plus a small per-student table for typing check times and settings (auto-submit). Row level security on and direct access revoked, like the other tables; students can only touch their own rows, and teachers read their own class the same way the existing teacher screens do (look at how fact_answers and the teacher pages do it). A saving function takes a **batch with an id made by the browser**, so a batch sent twice after a Wi-Fi drop is counted once (copy that idea from `record_fact_answers`). The server does not need to decide colours: it keeps the answers and the app works colours out with the shared code, so the bands stay in `shared/training/config.ts`.
2. **Server function / client:** a small saving path like the other games use (look at how Gem Keep or Wormholes send maths answers). Times are measured on the device. Answers go into a **queue in the browser** (wrapped so it works if storage is blocked) and are sent when the connection is back, so a session never breaks if Wi-Fi drops. Loading reads the student's answers back (the last few per fact are enough to rebuild colours, known days and review dates, so keep the rule in `shared/training/records.ts` the only place those are worked out). Keep a sensible limit on how much is stored and sent per student.
3. **Checking:** answers must match a session the shared code can rebuild from a seed (plan section 11). Save the session seed with each batch and have the server function reject answers for facts that aren't real or numbers that aren't possible (a negative or silly time). It doesn't need to prove a student's speed, only keep rubbish out.
